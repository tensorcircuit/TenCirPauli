# TenCirPauli Deep Audit — Round 3 (2026-08-05)

> **Scope.** An independent third-pass scan of the **current working tree** (Rust core `crates/tencir-pauli-core`, PyO3 bindings `crates/tencirpauli-native`, Python wrapper `python/tencirpauli`), run after the Round-2 archive (`audit-report-2026-08-04-round2.md`) and its completion review (`phase-8.5-audit-round2-completion-review-2026-08-05.md`). This pass deliberately excludes every item Round-1 (M1–M72) and Round-2 (R2-1–R2-17) marked Fixed/Closed/Deferred/Rejected; a finding appears here only if it is genuinely new, or shows an adopted fix is still incomplete in a way not already recorded.
>
> **Round-3 emphasis (per request).** (1) Python wrapper not thin enough — hot computation that should live in Rust; (2) cross-boundary call frequency — minimize crossings on normal call paths; (3) hot-path test gaps; (4) other performance bottlenecks; (5) implementation gaps / bugs; (6) dead / duplicate / orphaned code; (7) severe design flaws.
>
> **No code was changed.** This is a report only.

## 1. Executive Summary

**Method.** An 8-dimension ultracode workflow fanned out 8 finder agents (wrapper thickness, boundary frequency, test gaps, Rust perf, new correctness bugs, dead/duplicate code, FFI/binding design, and a deep-dive on the SPPS/Propagation/U1 engines). Each finder produced structured findings; every finding then went through an independent adversarial verifier that re-read the cited `file:lines` in the current tree, checked the R1/R2 exclusion ledger, and judged whether the fix's benefit clearly exceeds its cost/risk. The workflow returned **34 raw → 26 survivors / 8 dropped**. I then independently re-anchored each survivor against the source before writing this report; verification notes are inline per finding.

**Counts.**
- Raw round-3 findings: 34
- Survived adversarial verification: 26
- Dropped (refuted / partial-benefit-not-worth / in-exclusion-list / stale): 8

**Themes new in this pass.**
1. **The structured/Pauli read-back path round-trips owned Rust data through Python nested lists.** Every handle `materialize*` returns deeply nested `Vec<Vec<...>>`; the wrapper immediately feeds those lists back into a sibling FFI that re-parses them into a fresh Rust operator (`pauli_dense_array` / `pauli_csr_array` / `structured_hybrid_multiply` / `pauli_operator_native`). A flat-numpy ABI already exists (`pauli_canonicalize_batch_numpy`) but was never extended to handle read-back. This is the single largest class of finding (R3-FFI-1/2/3, THIN-1/2/3/4, CB-2) and is the core "wrapper is not thin / boundary frequency is too high" debt.
2. **Per-apply scratch reallocation on every matrix-free MVP hot path.** Generic charge, U1-lazy, and structured MVP `apply_into` all allocate scratch buffers inside the function body on every call; iterative solvers (the documented use case for these plans) pay O(iterations) identical-size heap allocations. The eager U1 and fast-fermion paths already prove these are avoidable.
3. **Test gaps on the public native engine surface.** `value_and_grad_adaptive` (SPPS), operator-level `MajoranaOperatorHandle.multiply`, and four `NativeU1CircuitPlan` methods (`probability`/`to_dense`/`probability_full`/`expectation`) have no numerical correctness test — only shape/metadata or indirect coverage.
4. **Dead `_native_data` storage representation + 7 dead helpers in `_StructuredOperator`** carrying a latent type-confusion bug; plus a dead split-re/im Pauli FFI quartet duplicated by the `_array` variants.

**Prioritized action list**
1. **Fix-now, correctness-adjacent test gaps:** SPPS adaptive exact-reference + divergent-budget test (R3-TG1, R3-D); Majorana operator multiply correctness test (R3-TG3); U1 plan-level method correctness tests (R3-TG5).
2. **Fix-now, hot-path perf (allocation churn):** generic charge per-apply scratch reuse (R3-D1); U1-lazy/structured scratch reuse (R3-D2); reverse-mode `output_indices` hashmap reuse (R3-D3); apply_fermions O(k·M)→O(k) parity (R3-D5).
3. **High-impact architecture / wrapper thinning:** handle-accepting `pauli_dense/coo/csr/mvp_from_handle` to skip the materialize→Python→rebuild round trip (R3-FFI-1); structured-handle `materialize_numpy` + GIL release (R3-FFI-3); `pauli_canonicalize_array_into_handle` (R3-FFI-2); wire the **already-existing** native `commutator`/`anticommutator` on fermion/boson/hybrid/majorana handles into the Python `commutator` (CB-2); fuse the three `_materialized_terms()` passes in `restrict_charge` (THIN-1).
4. **Dead-code cleanup:** delete the `_native_data` representation + 7 helpers (CB-1); remove the four dead split-re/im Pauli FFI functions (DEAD-1 / R3-FFI-4); zero-copy complex CSR/COO return (R3-FFI-6).
5. **Medium/low-cost wins:** structured `is_hermitian` native path (THIN-2); Pauli `__eq__`/`__hash__` short-circuit on native arrays (THIN-3); propagation final-term loop fusion (R3-F); native parameter-expression program for Propagation/SPPS (R3-B); SPPS adaptive per-term parallelism (R3-C); PackedKey in-place clone reduction (R3-D4); non-conserved charge borrowed-key hashmap (R3-D7); profile field validation test (R3-TG4).

## 2. Confirmed Findings

> Categories: **wrapper** = Python wrapper too thick / hot loop in Python; **boundary** = cross-boundary call frequency; **test-gap**; **perf** = Rust or Python performance; **ffi** = native binding design; **dead** = dead/duplicate code.

### 2.1 Wrapper thickness & cross-boundary frequency

#### R3-1 (THIN-1) — `restrict_charge` runs three Python passes over `_materialized_terms()` and rebuilds lists the Rust side re-clones — **wrapper / boundary · high**
**File:** `python/tencirpauli/charge.py:1471-1571, 1402-1421, 1424-1468`
**Summary.** `_restricted_transition_inputs` iterates `operator._materialized_terms()` once to build 12 per-term Python lists (1514-1550); `_termwise_charge_conserved` iterates the same terms again (1411-1421); `_fast_fermion_particles` iterates a third time (1460-1468). For a native-handle-backed structured operator, `_materialized_terms()` first calls `handle.materialize()` (1 native call) then `_terms_from_native_data` builds N `_Term` objects (each holding `FermionWord`/`BosonWord`/`QuditWeylWord` Python tuples-of-tuples) purely so the three loops can read their attributes back out. The resulting 12 Python lists are then handed to `NativeChargeSectorPlan.compile_mvp`, where `charge_terms_from_inputs` (`charge_sector.rs:48-88`) clones each `Vec` again into `ChargeTransitionTerm` structs. The intermediate `_Term` layer is pure overhead on both sides.
**Failure scenario.** Restricting a 2000-term `FermionOperator` to a charge sector: 1 native materialize → 2000 `_Term` allocations → 3 Python loops over 2000 terms → Rust re-clones 2000 `Vec<u32>`/`Vec<u8>`. On the `restrict_charge` hot path used in every sector-MVP research workflow.
**Fix.** Fuse the three loops into one pass building the 12 input lists while simultaneously computing `termwise_conserved` and `fast_fermion_particles`. For native-backed operators, source the 12 lists from `_hybrid_arrays`/`_fermion_arrays`/`_boson_arrays` (which already call `handle.materialize()` and return arrays without constructing `_Term` objects). Longer term, add a handle-taking native entry point that builds `ChargeTransitionTerm` directly in Rust.
**Benefit.** Removes 2 of 3 Python O(N) passes, eliminates N `_Term` allocations per `restrict_charge`, removes the Python→Rust re-clone of per-term arrays.
**Verdict.** CONFIRMED. Re-read `charge.py:1471-1571,1402-1421,1424-1468`; `structured.py:981-995,2264-2346`; `charge_sector.rs:48-88,150-185`. Caveats (do not change verdict): `_materialized_terms()` caches in `self._terms` so `_Term` allocation happens once not three times; the third pass only runs when `termwise_conserved` is true; `_termwise_charge_conserved` short-circuits on first violation. Not in any exclusion ledger.

#### R3-2 (THIN-2) — `StructuredOperator.is_hermitian` has no native path; materializes adjoint + two `to_dict` dicts and compares in Python — **wrapper · medium**
**File:** `python/tencirpauli/structured.py:1299-1313`
**Summary.** `_StructuredOperator.is_hermitian` builds `self.adjoint()` (one native call), then calls `self.to_dict()` and `other.to_dict()` (each materializing native data into a Python dict of tuple-keyed entries), then a Python key-set equality check and a Python per-key `abs(coef-coef)<=tol` loop. `PauliOperator` has a native `pauli_operator_is_hermitian`; the structured side has no equivalent, so even native-handle-backed structured operators pay full Python dict materialization + per-key comparison.
**Fix.** Add a native `is_hermitian(tolerance)` to `NativeFermionOperatorHandle`/`NativeBosonOperatorHandle`/`NativeHybridOperatorHandle` (the adjoint+comparison is straightforward in Rust over canonical arrays; `adjoint` already exists natively for all three) and dispatch to it from `_StructuredOperator.is_hermitian` when a native handle is present.
**Verdict.** CONFIRMED. The structured native side has `adjoint` (`structured.rs:169/461/603`) but no `is_hermitian`/`equal`. Not in exclusion list. The perf win is currently latent (`is_hermitian` is exercised in tests only on the Pauli side), but the wrapper-thickness defect is real and the fix is cheap.

#### R3-3 (THIN-3) — `PauliOperator.__eq__`/`__hash__` materialize all `PauliTerm` tuples for native-backed operators — **wrapper · medium**
**File:** `python/tencirpauli/pauli.py:595-601`
**Summary.** `__eq__` returns `self.nqubits == other.nqubits and self.terms == other.terms`; `__hash__` returns `hash((self.nqubits, self.terms))`. For a native-handle-backed operator, `.terms` (`pauli.py:362-372`) calls `_terms_from_packed_native` which materializes `handle.materialize()` into a tuple of `PauliTerm(PauliWord(...))` objects just to compare or hash. Equality could short-circuit on `term_count + nqubits` and compare native arrays directly; hashing could hash cached arrays.
**Fix.** Short-circuit `__eq__` on `nqubits` and `term_count` (already a non-materializing `handle.term_count` read) before touching `.terms`; when both operands have native handles or cached arrays, compare `(structures, re, im)` arrays via one `numpy.array_equal` per array (canonical form guarantees ordering consistency). For `__hash__`, hash `(nqubits, hash of cached arrays)`.
**Verdict.** CONFIRMED. `_terms` starts `None` for native-backed operators (`_initialize_native_handle` at 1357-1362), so `.terms` triggers full materialization. Cheaper primitives (`term_count` 582-590, `_arrays()` 544-563) already exist but are unused here.

#### R3-4 (THIN-4) — `_hybrid_arrays` terms-only path rebuilds 12 Python lists from `_Term` objects that native will re-clone — **wrapper · low**
**File:** `python/tencirpauli/structured.py:2213-2261`
**Summary.** When a structured operator has neither `native_handle` nor `native_data` with the 12-tuple shape (terms-only storage, e.g. `HybridOperator._from_terms` when any term has `mapped_fermion`, `structured.py:3132-3137`), `_hybrid_arrays` iterates `operator._materialized_terms()` and rebuilds 12 parallel Python lists, which `structured_hybrid_multiply`/`structured_hybrid_jordan_wigner` then pass back to Rust where they are re-parsed into native term structs. Same materialize-then-rebuild pattern as R3-1 for every hybrid multiply/scale/adjoint on terms-only operators.
**Fix.** Either store the 12-tuple `native_data` directly in `_from_terms` (skipping `_Term` construction), or add a native `canonicalize-from-terms` entry point consuming the `_Term` fields in one batch. At minimum, cache the 12-list form alongside `_terms` so repeated `_hybrid_arrays` calls do not rebuild.
**Verdict.** CONFIRMED. The terms-only path exists because `structured_hybrid_canonicalize`'s FFI input does not accept `mapped_fermion` codes, only fermion/boson/qubit/qudit factors — so `mapped_fermion` operators cannot be canonicalized natively. Low severity: minimum-cost fix (caching) only helps when the same operand is reused across operations; deeper fixes need native work.

#### R3-5 (CB-1) — Entire `_native_data` storage representation in `_StructuredOperator` is dead code; 7 dead helpers + a latent type-confusion bug — **dead · high**
**File:** `python/tencirpauli/structured.py:900-995, 1087-1104, 1176-1181, 1246-1249, 2158-2212, 2354-2543`
**Summary.** `_StructuredOperator._native_data` is always `None` on every real instance because no constructor ever passes `native_data=` to `__init__`; every structured operator stores its data in `_native_handle` instead. The tests explicitly assert this (`tests/test_structured_algebra.py:44-47`). Yet a full parallel code path branches on `if self._native_data is not None`, and 7 helper functions exist only to serve that never-taken branch: `_scaled_native_data` (2354), `_scale_native_structured` (2438), `_fermion_raw_from_data` (2450), `_boson_raw_from_data` (2461), `_hybrid_raw_from_data` (2473), `_add_native_structured` (2516), `_adjoint_native_structured` (2546). Worse, `_scale_native_structured`/`_adjoint_native_structured` pass a `StructuredNativeData` tuple into `_hybrid_from_native` which only accepts a `NativeHybridOperatorHandle` — they silence the type checker with `cast(Any, ...)`, which is itself evidence the path was never exercised; wiring it up would store a tuple as `_native_handle` and `AttributeError` on `.term_count`.
**Fix.** Delete the `native_data` parameter of `__init__` and the `_native_data` field; remove all `if self._native_data is not None` branches and the 7 dead helpers; collapse `_hybrid_arrays` to its handle-materialize and terms-materialize arms. Keep `_terms_from_native_data` (still live via the handle-materialize arm at line 987).
**Benefit.** Removes ~250 lines of unreachable code from the algebra hot path, eliminates a latent `AttributeError`, makes the handle-vs-terms storage model unambiguous.
**Verdict.** CONFIRMED. Repo-wide grep for `native_data=` returns zero hits; `tests/test_structured_algebra.py:44-47` assert `_native_data is None`. The `cast(Any, ...)` at 2443/2597 is the smoking gun. Not in exclusion list.

#### R3-6 (CB-2) — Structured/Majorana `commutator`/`anticommutator` do 4 native crossings instead of calling the existing native single-pass commutator — **boundary · high**
**File:** `python/tencirpauli/structured.py:1203-1240`; `python/tencirpauli/majorana.py:427-448`
**Summary.** `_StructuredOperator.commutator` (1210-1211) and `MajoranaOperator.commutator` (434-437) compute `self.multiply(other)` and `other.multiply(self)` separately: 2 native multiplies + 1 native scale + 1 native add = **4 cross-boundary calls and 2 full term-expansion passes** per commutator. The verifier discovered that the finder's stated root cause ("the native handles only expose add+multiply") is **false**: all four structured handles *already* expose native `commutator` and `anticommutator` (`structured.rs:170/196` Fermion, `:800/~819` Hybrid, `:979/~998` Boson; `majorana.rs:86/112`), implemented as single-pass `binary_*_terms(..., sign)` Rust routines. The actual bug is a **Python-side wiring gap**: `commutator`/`anticommutator` never dispatch to `self._native_handle.commutator(...)` the way `multiply` already dispatches to `self._native_handle.multiply(...)`, and `_native.pyi` only declares `commutator`/`anticommutator` for `NativePauliOperatorHandle` (lines 27-32), omitting them for the fermion/boson/hybrid/majorana stubs.
**Failure scenario.** `examples/research/bch_convergence/run_structured.py:226-234` nests these commutators on `FermionOperator`/`BosonOperator` in a 4th-order BCH series; each nesting level doubles the redundant product expansions. A native single-pass commutator would halve both crossings (4→1) and intermediate allocations.
**Fix.** A few-line Python change: in `_StructuredOperator.commutator`/`anticommutator` (and the majorana analog), when both operands share a matching native handle, call `self._native_handle.commutator(other._native_handle, max_bytes)` directly, mirroring how `multiply` dispatches. Add the missing `commutator`/`anticommutator` entries to the fermion/boson/hybrid/majorana stubs in `_native.pyi`. No new Rust needed.
**Verdict.** PARTIAL→CONFIRMED-as-rewritten. The inefficiency is real and worth fixing; the finding's diagnosis was wrong but the verifier corrected it. The native single-pass methods exist and are simply unwired.

### 2.2 Test gaps

#### R3-7 (R3-TG1) — `NativeSPPSEngine.value_and_grad_adaptive` has no accuracy / exact-reference correctness test — **test-gap · high**
**File:** `tests/test_spps.py:81-108, 194-224`; `tests/test_circuit_facades.py:174-183`
**Summary.** The adaptive SPPS estimator is exercised only for replay stability, metadata shape, and memory guards; its value and gradient are never compared against an exact reference, unlike the fixed-budget `value_and_grad` which IS checked against `exact_value_and_gradient` (`test_spps.py:44-54`). A regression in the adaptive budget-growth / convergence logic (wrong replicate count, wrong `gradient_tolerance` comparison, a sign or coefficient aggregation bug specific to the multi-replicate adaptive path) would pass every existing test because no assertion binds value/gradient to a known-correct number.
**Fix.** Add a test mirroring `test_fixed_estimator_matches_exact_single_term_expectation`: single-rotation engine, `value_and_grad_adaptive` with tight `gradient_tolerance` and large `max_samples_per_term`, assert `estimate.value == approx(np.cos(theta))` and `estimate.gradient[0] == approx(-np.sin(theta))`.
**Verdict.** CONFIRMED. Verified all 5 call sites in `test_spps.py` + benchmark; none asserts value/gradient against the exact reference. R2-6 is a different documented limit (proxy/converged native-space mismatch).

#### R3-8 (R3-TG3) — `NativeMajoranaOperatorHandle.multiply` has no correctness test (only shape-only benchmark) — **test-gap · high**
**File:** `tests/test_majorana_mapping.py:102, 270, 24`
**Summary.** The operator-level native Majorana product (a distinct entry from `MajoranaWord.multiply`) is exercised only by a shape-only benchmark (`benchmarks/python/test_majorana_mapping_charge_benchmark.py:324-328`) and a laziness assertion (`tests/test_majorana_mapping.py:24` asserts `operator.multiply(operator)._terms is None`, not a value). Its numerical result is never compared to a reference. The native kernel `multiply_majorana_terms` (`majorana.rs:406`) performs multi-term coefficient aggregation with a reordering-sign hashmap — logic distinct from the single-word `multiply_words` that IS tested.
**Fix.** Build a multi-term `MajoranaOperator`, compute `left.multiply(right)` via the native handle, materialize to dense via `to_fermion().compile('dense')`, compare to the matrix product of left/right dense references.
**Verdict.** CONFIRMED. This kernel backs `commutator`/`anticommutator` and BCH-style aggregation; ships with zero numerical coverage.

#### R3-9 (R3-TG4) — `NativePropagationEngine.profile`: 5 of 7 returned diagnostic fields are never validated — **test-gap · medium**
**File:** `tests/test_propagation.py:260-262`
**Summary.** `profile` returns `(value, initial_term_count, final_term_count, peak_term_count, estimated_peak_bytes, final_weight_counts, kernel_seconds)`; tests assert only `value` and `final_term_count`. `peak_term_count`, `estimated_peak_bytes`, `final_weight_counts`, `kernel_seconds`, `initial_term_count` are never checked.
**Fix.** Extend the existing test: assert `initial_term_count == len(observable.terms)`, `peak_term_count >= final_term_count`, `estimated_peak_bytes >= 0` and monotone in observable size, `final_weight_counts` sums to `final_term_count`.
**Verdict.** CONFIRMED. Caveat: `peak_term_count` is a reporting surface, not the `max_bytes` enforcement mechanism (the guard runs inside the engine independently), so the failure-scenario's "under-budgeted memory guards" is overstated; the test-gap is nonetheless real.

#### R3-10 (R3-TG5) — `NativeU1CircuitPlan.probability` / `to_dense` / `probability_full` / `expectation` have zero direct tests — **test-gap · high (benefit: medium)**
**File:** `tests/test_u1_circuit.py:186, 241`; `tests/test_phase8_api.py:269`
**Summary.** Four distinct native plan entry points (`u1_circuit.rs:97-180`) are never exercised by any test; only `run`, `run_cached`, and `value_and_grad` on the plan are covered, and the `U1Circuit` facade uses the parallel `run_cached` + `NativeU1FinalState` implementation instead of these plan-level methods. The verifier softened severity: the four wrappers are thin glue delegating to the same core functions (`probability_from_state`, `to_dense_from_state`, `probability_full_from_state`, `expectation_from_state`, `build_canonical_operator`) already exercised by the cached facade / `value_and_grad`, with parameter-binding slices byte-identical to the tested `NativeU1CircuitPlan.run`. So the genuinely untested surface is the delegation wiring, not the sector-indexing/parameter-binding logic.
**Fix.** A few `assert_allclose` lines: `plan.probability(initial, params) == |plan.run(initial, params)|**2`; `plan.state_full(initial, params)[basis] == plan.run(initial, params)`; `plan.expectation(initial, obs, params) ≈ vdot(dense, obs.dense() @ dense)`.
**Verdict.** PARTIAL. The four methods are public (`u1_circuit.py:260-328`) and callable directly on a compiled plan; a cheap test closes a real but modest blind spot.

### 2.3 Rust core performance

#### R3-11 (R3-D1) — Generic charge MVP reallocates 5 scratch buffers on every `apply_into` call — **perf · high**
**File:** `crates/tencir-pauli-core/src/charge.rs:1502-1507`
**Summary.** `apply_charge_mvp_from_prepared_plan_into` allocates `source`, `destination`, `remaining`, `candidate_remaining` `Vec`s plus a `destinations: FxHashMap` fresh on every apply call, even though `PreparedChargeTransitionPlanLayout` was designed to validate once for repeated execution. An iterative solver calling `apply` thousands of times pays thousands of identical-size heap allocations. This is the precise location the Round-2 completion review noted for generic charge lazy (the verifier confirmed it is still present and not formally tracked as an open item).
**Failure scenario.** A Lanczos/CG inner loop calling apply 5000× on a sector with `axis_count=12`, `constraint_count=2`: 4 `Vec` + 1 `HashMap` allocations per iteration of identical sizes, dominating per-iteration overhead for small-to-medium sectors.
**Fix.** Introduce a reusable applier struct (or `&mut` scratch buffers threaded through `apply_into`) holding source/destination/remaining/candidate_remaining/destinations, allocated once. The `fast_fermion_plan` path (`charge.rs:1462-1467`) already allocates nothing per `apply_into` — proves feasibility.
**Verdict.** CONFIRMED. Within one call the buffers are reused via `clear()`, but across calls dropped. Not R2-4 (different file/issue).

#### R3-12 (R3-D2) — U1-lazy and structured MVP `apply_into` share the same per-apply scratch reallocation pattern — **perf · medium**
**File:** `crates/tencir-pauli-core/src/sector.rs:638-642`; `crates/tencir-pauli-core/src/structured.rs:1544-1545`
**Summary.** `U1LazyMvpPlan::apply_into` allocates `source_active`, `source_words`, `destination_words`, `aggregate` `Vec`s on every call; `StructuredMvpPlan::apply_into` allocates `digits` and `output_digits` on every call. Both plans are immutable objects explicitly meant for repeated matrix-free MVP in iterative solvers, yet neither caches scratch across calls. The eager `U1MvpPlan::apply_into` (`sector.rs:700`) is allocation-free per apply and is the model to match.
**Fix.** Caller-managed `Scratch` struct passed via a new `apply_into_with_scratch` (option (b) `RefCell` would make the plan `!Sync`, breaking the `py.allow_threads(|| &self.plan...)` FFI pattern — avoid).
**Verdict.** CONFIRMED. Not R2-15 (that was the budget test, not scratch reuse).

#### R3-13 (R3-D3) — `reverse_frame` rebuilds the `output_indices` hashmap on every gate of the reverse pass — **perf · medium**
**File:** `crates/tencir-pauli-core/src/propagation.rs:1378-1381`
**Summary.** `reverse_frame` allocates and fills a fresh `FxHashMap<PackedKey, usize>` of size `output.len()` on every call; `value_and_grad` calls `reverse_frame` once per gate (single-gate blocks at 270) or per checkpoint step (313), so a tape with G gates triggers G hashmap allocations and G full key-index rebuilds. `PackedKey::Wide` (`>128` qubits) holds two `Vec<u64>`, so each insertion is a heap clone for wide tapes; for `Inline` the clone is cheap but the allocation+rehash of ~`output.len()` entries is still repeated per gate.
**Fix.** Thread a reusable `&mut FxHashMap<PackedKey, usize>` scratch through `reverse_frame` (`clear()` + repopulate per call; `clear` retains capacity). The `PackedKey` clones for insertion remain, but allocation is paid once.
**Verdict.** CONFIRMED. The claim that allocations "dominate" is slightly overstated (per-input `visit_retained_edges` traversal is comparable), but the rebuild is a legitimate constant-factor win on the reverse-AD hot path. Genuinely new (R2-4 is a different propagation.rs issue).

#### R3-14 (R3-D4) — Hot propagation apply paths clone the full `PackedKey` per transition (allocates for >128-qubit systems) — **perf · medium (benefit: narrow)**
**File:** `crates/tencir-pauli-core/src/propagation.rs:1350, 1483, 1720`
**Summary.** In `apply_operation`'s `CustomPtm` branch (1350), `visit_retained_edges` CustomPtm (1483), and `multiply_by_generator` (1720), the code does `let mut key = term.key.clone()` per transition per term per gate. For `PackedKey::Wide` (`nqubits > 128`) each clone heap-allocates two `Vec<u64>`. The `Clifford1`/`Clifford2` branches already use `apply_*_in_place` (1282/1295) and avoid clones because Clifford is 1:1.
**Verifier caveats (lower the benefit).** (1) The finder's "O(terms·branching·gates)" count is inflated by ~branching factor `b`: for `b` distinct output transitions you need `b` owned keys; you can save at most ONE clone per term by moving `term.key` for one transition. Real savings are O(terms·gates). (2) The sketched `multiply_by_generator_into` in-place variant does **not** eliminate the Rotation clone, because Rotation pushes BOTH `term.key` (cosine, moved) AND the product (sine, cloned) into the same `contributions` Vec simultaneously — eliminating the Rotation clone needs save/restore of local codes or restructuring `aggregate`.
**Fix.** Add in-place variants for `CustomPtm` (the cleaner win); for `Rotation`, restructure to move `term.key` and revert local codes after pushing the product, or insert incrementally into `aggregate`'s hashmap.
**Verdict.** CONFIRMED with the above caveats. For explicitly-supported `>128`-qubit tapes the savings (one `Vec`-pair allocation per term per gate, plus one in the reverse pass) are meaningful; for `≤128`-qubit (`Inline`) the clone is a cheap memcpy so impact is narrow-system-only.

#### R3-15 (R3-D5) — `apply_fermions` recomputes per-mode parity by summing lower modes (O(k·M) per term), unlike the fast fermion path's O(1) `count_ones` — **perf · medium**
**File:** `crates/tencir-pauli-core/src/charge.rs:368-371`
**Summary.** In `apply_fermions` the generic-charge fermion parity is computed as `(0..mode).map(|lower| occupations[positions[lower]]).sum::<u64>() & 1` for each mode applied, recomputed from scratch each mode. The fast fermion path (`apply_fast_fermion_term` at `charge.rs:1003`) uses `(destination & fast_fermion_lower_mask(mode)).count_ones() & 1` which is O(1) per mode. `apply_fermions` sits on a hot compile path: called inside `for column in 0..dimension { for term in terms }` at `charge.rs:1131` and `:1277`, so hit `dimension × terms` times.
**Fix.** Maintain a running prefix-parity (or a small bitmask of occupied lower modes) updated incrementally as each mode is created/annihilated, so each mode's parity lookup is O(1); or precompute a positions-sorted prefix-occupancy array per `apply_fermions` call. Non-trivial (occupations mutate between applies; order is physics-fixed) — a Fenwick tree or bitset gives a correct sub-linear-per-apply solution.
**Verdict.** CONFIRMED. The headline says O(k²) but the inner sum is over `0..mode` (sector fermion-mode count M), so it is O(k·M) per term; the failure-scenario text acknowledges this.

#### R3-16 (R3-D7) — Non-conserved charge MVP clones the destination occupation `Vec` per term to use as hashmap key — **perf · low**
**File:** `crates/tencir-pauli-core/src/charge.rs:1563-1565`
**Summary.** In `apply_charge_mvp_from_prepared_plan_into`'s non-termwise-conserved branch, each surviving term does `destination.clone()` to insert into `destinations: FxHashMap<Vec<u64>, Complex64>`. That is one `axis_count`-length `Vec` clone per term per column, i.e. `dimension × terms.len()` clones per apply call. The conserved path (1519-1546) avoids this by ranking directly.
**Failure scenario.** Apply a non-particle-conserving structured operator (e.g. hopping `x(0)x(1)+y(0)y(1)`, whose X/Y codes make `_termwise_charge_conserved` return False — exercised by `tests/test_charge.py:207-242`) on a sector of dimension 4096 with 20 terms and `axis_count=10`: ~82000 clones of a 10-u64 `Vec` per apply, plus per-insert `Vec` rehashing.
**Fix.** Use a borrowed-key hashmap (`hashbrown` `raw_entry` / `entry_ref`, or an arena + slice-keyed map) so the `destination` slice is the key without cloning.
**Verdict.** CONFIRMED. Low severity; touches a correctness-sensitive path that already has test coverage.

### 2.4 FFI / binding design

#### R3-17 (R3-FFI-1) — Handle `materialize*` methods return nested Python lists; every read-back path (dense/coo/csr/mvp) materializes-then-rebuilds across the boundary — **ffi · high**
**File:** `crates/tencirpauli-native/src/operator.rs:86-96`; `python/tencirpauli/pauli.py:544-563, 924-1013`
**Summary.** `NativePauliOperatorHandle.materialize`/`materialize_arrays`/`materialize_strings` all return deeply nested Python sequences (`Vec<Vec<u8>>` / `Vec<Vec<u64>>` / `Vec<String>` plus split re/im `Vec<f64>`). There is no numpy/flat variant for handle read-back, unlike the standalone `pauli_canonicalize_batch_numpy` which already proves the flat-array ABI is better. Consequently every `PauliOperator.dense`/`coo`/`csr`/`mvp`/`backend_mvp_plan` call on a handle-backed operator does `handle.materialize_arrays()` → N Python lists of `nqubits` boxed u8 ints → re-marshals those nested lists back into native as `Vec<Vec<u8>>` via `pauli_dense_array`/`pauli_csr_array`, which immediately calls `build_canonical_operator` (`convert.rs:147`) re-converting the nested lists into a fresh `PauliOperator` and re-running `from_canonical_terms`. The handle already owns a canonical `PauliOperator`, so this is a pure materialize→Python→re-marshal→rebuild round trip (with a bonus redundant re-canonicalization).
**Failure scenario.** Build a large handle-backed PauliOperator via `add()`/`multiply()`, then call `.coo()`/`.csr()`/`.mvp()`: ~`term_count × nqubits` Python int allocations, re-marshalled back into Rust. (`_arrays()` caches on the instance at `pauli.py:548-558`, so `materialize_arrays` itself is paid once per operator — but the Python→Rust re-marshalling + `build_canonical_operator` rebuild occurs on **every** dense/coo/csr/mvp call.)
**Fix.** Add handle-accepting FFI: `pauli_dense_from_handle(&NativePauliOperatorHandle, max_bytes) -> (usize, PyArray1<Complex128>)`, and analogs for coo/csr/mvp/backend_mvp_plan; in `PauliOperator.dense/coo/csr/mvp`, branch on `self._native_handle` and call the handle variant directly (mirroring the existing `_as_native_handle` dispatch for `add`/`multiply`). Add `materialize_numpy()` on the handle returning flat `(codes, x, z, coeffs)` arrays so `.terms` can be built without per-term Python list/int creation.
**Benefit.** Eliminates one full nested-list materialization + one nested-list re-marshalling + one redundant `from_canonical_terms` per matrix/MVP compile on lazy operators; expected 2-10× on the dense/coo/csr hot path for handle-backed operators.
**Verdict.** CONFIRMED. Caveat: the 10000-term × 20-qubit `.dense()` example is partly infeasible (20-qubit dense = 16 TiB, rejected by `max_bytes`); the inefficiency bites realistically for coo/csr/mvp on large operators and dense on smaller qubit counts. Central defect genuine. Not in exclusion list.

#### R3-18 (R3-FFI-2) — `pauli_canonicalize_array` accepts numpy input but returns nested `Vec<Vec<u8>>`, immediately re-marshalled back to native — **ffi · medium**
**File:** `crates/tencirpauli-native/src/operator.rs:200-231`; `python/tencirpauli/pauli.py:1336-1349, 354, 407`
**Summary.** `pauli_canonicalize_array` takes a C-contiguous `PyReadonlyArray2<u8>` (zero-copy input, good) but its return type `CanonicalizeOutput = (Vec<Vec<u8>>, Vec<f64>, Vec<f64>)` marshals the canonical structures out as N Python lists of `nqubits` u8 ints. `_initialize_operator` (`pauli.py:1342-1348`) then immediately feeds those nested lists into `pauli_operator_native(structures, ...)` which re-converts them to Rust `Vec<Vec<u8>>`. The array fast-path is thrown away on output. Exercised by the primary large-batch construction paths (`__init__` array fast-path `pauli.py:354-355`, `from_code_arrays` `pauli.py:407-411`).
**Fix.** Return a `NativePauliOperatorHandle` directly from a new `pauli_canonicalize_array_into_handle` (canonicalize straight into the handle, skip the Python-list intermediate entirely — the wrapper always wants a handle); or return flat `(PyArray1<u8> codes, PyArray1<Complex128> coeffs)` like `pauli_canonicalize_batch_numpy`.
**Verdict.** CONFIRMED. The flat ABI already exists at `operator.rs:287-339`.

#### R3-19 (R3-FFI-3) — Structured handles (fermion/boson/hybrid/majorana) `materialize` return deeply nested Python sequences with no numpy variant and no GIL release during clone — **ffi · high**
**File:** `crates/tencirpauli-native/src/structured.rs:196-204, 511-527, 619-622`; `crates/tencirpauli-native/src/majorana.rs:133-136`
**Summary.** `NativeFermionOperatorHandle.materialize` returns `(Vec<Vec<u32>>, Vec<Vec<u32>>, Vec<f64>, Vec<f64>)`; `NativeBosonOperatorHandle` returns `Vec<Vec<(u32,u32,u32)>>` (list of lists of 3-tuples); `NativeMajoranaOperatorHandle` returns `Vec<Vec<u64>>`; `NativeHybridOperatorHandle.materialize` returns a **12-element tuple** of mostly `Vec<Vec<...>>` with mixed `bool`/`Vec<u32>`/`Vec<(u32,u32,u32)>`/`Vec<u8>` entries. None has a numpy/flat variant. None uses `py.allow_threads` for the internal `.clone()` + `split_complex`, unlike `NativePauliOperatorHandle.materialize` (`operator.rs:86-96`) which does. `_terms_from_native_data` (`structured.py:2311-2346`) then does a 12-way zip reconstructing `FermionWord`/`BosonWord`/`QuditWeylWord` per term.
**Failure scenario.** Accessing `.terms` on a hybrid operator that is the product of two large hybrid operators: materialize crosses the boundary with 10+ separate `Vec<Vec<...>>` containers, each element of each row becoming a Python tuple/list of boxed ints, then 12-way zip typed-word construction — all under the GIL with no `allow_threads` on the Rust clone.
**Fix.** Provide `materialize_numpy()` variants returning flat `PyArray1`s (offsets+values for variable-length rows, or a ragged COO layout) and/or a single opaque packed-`PyArray1<u8>` buffer with a documented layout descriptor. At minimum wrap the clone+split in `py.allow_threads` as the Pauli handle already does.
**Verdict.** CONFIRMED. Honest caveat: the dominant cost is PyO3's own `Vec<Vec<...>>` → Python-list conversion which inherently holds the GIL, so the minimal `allow_threads` wrap only saves the clone+split (modest); the order-of-magnitude win requires the sketched numpy/flat variant (higher cost). The minimal fix is benefit>cost and low-risk; the full numpy variant is justified for large hybrid products.

#### R3-20 (R3-FFI-6) — Charge eager `csr`/`coo` rebuild complex values via `split_complex` + map-zip instead of zero-copy reinterpret — **ffi · low**
**File:** `crates/tencirpauli-native/src/charge_sector.rs:458-501`
**Summary.** `NativeChargeEagerMvpPlan.csr`/`.coo` hold `self.values` as `Vec<Complex64>` (`#[repr(transparent)]` over `(f64,f64)`, layout-identical to numpy `Complex64`). They call `split_complex` to get `(Vec<f64>, Vec<f64>)` then map-zip into `Vec<NumpyComplex128>` via `NumpyComplex128::new(re, im).collect()`, allocating two intermediate f64 vectors and a fresh complex vector, then `PyArray1::from_vec`. A single `PyArray1::from_vec(py, self.values.clone())` would avoid both the split and the re-zip — `numpy::Complex64` IS `num_complex::Complex64` (the numpy crate re-exports it), so the types are identical and a direct `from_vec` is sound.
**Failure scenario.** Every `csr()`/`coo()` call on a large restricted operator allocates 3 transient length-N vectors purely for format shuffling; for 1e7 transitions ~240 MB transient per call.
**Fix.** Replace `split_complex` + zip with `PyArray1::from_vec(py, self.values.clone())` directly (or `from_owned_array` to move without copy). One-line substitution per method, near-zero risk.
**Verdict.** CONFIRMED. Type identity verified at `scalar.rs:1` and `charge_sector.rs:3`. Not R2-7 (dead charge FFI) or R2-14 (eager guard).

### 2.6 Engine deep-dive (Propagation / SPPS / U1)

#### R3-22 (R3-B) — Propagation/SPPS plans evaluate symbolic angle Jacobians in a Python loop while U1 does it natively — **perf · medium**
**File:** `python/tencirpauli/propagation_circuit.py:154-180`; `python/tencirpauli/spps_circuit.py:59-71`; `python/tencirpauli/circuit.py:170-203`
**Summary.** `PropagationCircuitPlan._native_parameters` and `SPPSCircuitPlan._native_parameters` iterate `self._dynamic_angles` in a Python for-loop, calling `_evaluate_angle` per angle (which allocates a fresh `nparameters`-length Jacobian vector per `Parameter` and recurses per `ParameterExpr`). The U1 circuit instead has a native `CircuitProgram` that evaluates parameters and reverse-propagates the adjoint entirely in Rust (`u1_circuit.rs:627` `evaluate_parameters`, `:693` `reverse_parameter_program`). The propagation/SPPS engines also materialize a dense `N × nparameters` Jacobian that is structurally sparse.
**Failure scenario.** A 100-angle parameterized propagation/SPPS circuit in a 1000-step optimizer loop: ~1e5 Python-level Jacobian allocations plus `_evaluate_angle` recursion overhead, all of which the U1 path avoids.
**Fix.** Encode the dynamic-angle expression DAG into a native parameter program (like U1's `CircuitProgram`/`ParameterExprNode`) and have the propagation/SPPS native engines accept it, returning both evaluated angles and the slot-space gradient so Python only does the final `jacobian.T @ gradient` chain (or have the native engine own the chain too). Mirrors the existing U1 architecture.
**Verdict.** CONFIRMED. Not R2-5 (that fixed the value-only path via `_native_values`; this targets the gradient path, untouched).

#### R3-23 (R3-C) — SPPS `value_and_grad_adaptive` serializes across terms while fixed `value_and_grad` parallelizes — **perf · medium**
**File:** `crates/tencir-pauli-core/src/spps.rs:458-501`
**Summary.** The adaptive loop iterates `term_index 0..term_count` sequentially, calling `run_samples_batched` twice per term (left/right replicates) with a single shared `&mut scratch`. By contrast fixed `value_and_grad` (`spps.rs:373-393`) uses `stats.par_iter_mut().enumerate()` to parallelize across terms. For small per-term budgets (initial `samples_per_term` as low as 2) the inner chunk-parallel path never activates (`end-start <= SAMPLE_CHUNK_SIZE=256`), so the entire adaptive loop runs on one thread.
**Failure scenario.** 200-term Hamiltonian, `initial_samples_per_term=8`: 200×2×8 = 3200 single-threaded path simulations per doubling iteration, while the same circuit's fixed `value_and_grad` parallelizes across all 200 terms. ~16× slower per equivalent sample count on a 16-core machine.
**Fix.** Parallelize the per-term (left,right) pair across rayon workers: collect `(term_index, old, next)` tasks for terms needing more samples, run via `par_iter` with per-worker `PathScratch`, keeping the left/right replicate pair for one term on one worker. The fixed path proves per-term work is independent and safely parallelizable.
**Verdict.** CONFIRMED. Not R2-6 (different documented-limit issue).

#### R3-24 (R3-D) — SPPS adaptive has no test exercising per-term divergent budgets or exact value/gradient reference — **test-gap · low**
**File:** `tests/test_spps.py:81-108, 194-224`
**Summary.** The adaptive path's defining feature is that terms with larger gradient proxies get more samples (`spps.rs:510-514` sets `needs_more` per term). Every existing adaptive test uses observables where all terms converge to the same budget: `test_adaptive_budget_and_empty_observable_contract` asserts `samples_per_replicate in ((8,),(16,),(32,))`; `test_composite_bloch_terminal_reduction_and_adaptive_replay` asserts `((8,8),(16,16))`. No test verifies the divergent-budget code path, and no test compares adaptive value/gradient against an exact reference. The `combine_adaptive` Rust unit test (`spps.rs:1099-1111`) only checks the standard-error formula for a single term with equal left/right counts.
**Failure scenario.** A regression in per-term `needs_more` logic (wrong proxy comparison, off-by-one in budget doubling, a bug in `combine_adaptive` when left.count != right.count across terms with different budgets) would not be caught.
**Fix.** Add a test with two observable terms of very unequal coefficient magnitude (e.g. 1.0 and 1e-6) so their gradient proxies differ by orders of magnitude, assert `samples_per_replicate` is non-uniform (e.g. `(max, initial)`) and that value/gradient match `exact_value_and_gradient` within the estimator's standard error.
**Verdict.** CONFIRMED. Distinct from R3-7 (exact-reference gap): this one specifically targets the divergent-budget branch.

#### R3-25 (R3-F) — Propagation `value_and_grad` computes `expectation_of_key` twice per final term (value + lambda init) — **perf · low**
**File:** `crates/tencir-pauli-core/src/propagation.rs:239-249`
**Summary.** `value` is computed via `expectation_from_dynamic_terms(&current, ...)` which calls `expectation_of_key` per term; then `lambda` is initialized by iterating `current` again and calling `expectation_of_key` per term. `expectation_of_key` (`propagation.rs:1818-1840`) is an O(nqubits) fold for Bloch/ComputationalBasis states, so each final term's expectation is computed twice.
**Fix.** Fuse the two loops: compute `e = expectation_of_key(term.key, ...)` once per term, accumulate `value += term.coefficient.re * e` and push `e` to `lambda`. Left-to-right summation order is preserved (both passes use iterator order), so no floating-point result change.
**Verdict.** CONFIRMED. Low severity (small relative to full forward+reverse propagation) but the fix is essentially free and risk-free.

## 4. Cross-cutting assessment

**Where the wrapper is thinnest (good).** The U1 circuit engine is the architectural exemplar: a native `CircuitProgram` evaluates parameters and reverse-propagates the adjoint entirely in Rust, producing the slot-space gradient without a dense Jacobian. The Pauli handle's `add`/`multiply`/`commutator` dispatch to native single-pass routines. The eager `U1MvpPlan::apply_into` and the fast-fermion charge path allocate nothing per apply.

**Where the wrapper is thickest (the debt).** Two structural patterns account for the bulk of this round's findings:
1. **Read-back round-tripping.** Every structured/Pauli handle `materialize*` returns nested Python lists; the wrapper rebuilds typed Python word objects from them, then feeds those lists back into a sibling FFI that re-parses them into a fresh Rust operator. The handle already owned canonical Rust data. R3-17/18/19 + R3-1/2/3/4 + R3-6 are all instances of this. The fix is consistent: add handle-accepting and/or flat-numpy FFI variants so the data never leaves Rust.
2. **Per-call scratch allocation on matrix-free plans.** Generic charge, U1-lazy, structured MVP, and the reverse-AD `output_indices` map all allocate scratch in the function body instead of threading a reusable buffer. R3-11/12/13. The eager U1 and fast-fermion paths prove the fix shape.

**Correctness posture.** No new silent-numerical-error was found on a live hot path (unlike R2-2/R2-3 last round). The remaining correctness exposure is *untested* code rather than *wrong* code: the SPPS adaptive estimator, the Majorana operator product, and four U1 plan-level methods ship without value/gradient accuracy bindings. R2-4 (projected-batch estimate overflow) remains the only formally-open item from prior rounds; it is unchanged here (see §5 Open item carried forward).

## 5. Open item carried forward

> **R2-4 — projected propagation batch storage-estimate overflow. Status: STILL OPEN (not resolved by Round 2 or Round 3).**

- **Location:** `crates/tencir-pauli-core/src/propagation.rs:572-600` (`PropagationBatch` storage-estimate path).
- **Defect:** The R2-4 fix only converted the *first* estimate overflow to checked arithmetic, but the sentinel value `usize::MAX` is still merged into the subsequent `checked_mul` / `checked_add` chain, so any single overflow in the estimate chain causes the whole estimate to fail with `OverflowError: integer overflow while estimating propagation batch storage` — **even when the post-projection (`max_weight`-truncated) Pauli space is polynomial-sized and well within `max_bytes`**.
- **Repro (stable, from the Round-2 completion review):** 64 qubits, 64 rotations, `max_weight=1`, a single weight-1 observable, `max_bytes=None` → `PropagationBatch` construction raises `OverflowError`.
- **Disposition across rounds:**
  - Round 2 (`audit-report-2026-08-04-round2.md`): filed as R2-4, fix-now.
  - Round-2 completion review (`phase-8.5-audit-round2-completion-review-2026-08-05.md`): judged **FAIL** — "仍稳定报 `OverflowError`", and the review's overall conclusion is *conditional acceptance* explicitly contingent on R2-4 being fixed before claiming Round 2 / Phase 8.5 fully closed.
  - Round 3 (this report): **UNCHANGED / NOT TOUCHED.** Round 3 did not modify any source code (report-only) and did not attempt the fix. R2-4 is intentionally NOT re-filed here as a new finding (it is on the exclusion ledger as a known-open item); this section records its carried-forward status for the next remediation round.
- **Fix direction (not applied):** treat overflow as a first-class signal propagated through the estimate pipeline (on overflow, stop accumulating and fall through to the `max_bytes` comparison against the projected-space estimate), instead of feeding `usize::MAX` into further checked arithmetic. Requires a careful sweep of all merge points in the estimate chain, not just the first.

**Recommended sequencing.** The test gaps (R3-7/8/9/10/24) are cheap and protect every subsequent change — do them first. Then the allocation-churn fixes (R3-11/12/13/15), which are localized and low-risk. Then the wrapper-thinning architecture work (R3-17/18/19/6/1), which is the highest-impact but also the most involved. The dead-code deletions (R3-5/21) can proceed any time independently.
